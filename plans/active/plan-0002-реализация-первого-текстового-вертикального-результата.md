### A-002. Политика обработки AI-данных

Используется OpenAI API, не ChatGPT UI. Добровольное data sharing для обучения/улучшения не включается. Передаётся только минимальный текст и текущий контекст одной задачи; секреты, пароли, access tokens, API keys и Supabase credentials запрещены. Пользовательский текст, prompt, context и сырой AI response не пишутся в application logs. Provider memory, conversations, vector stores, file storage/search, web search, дополнительные tools и orchestration не используются. AI output валидируется локально. Training policy, abuse-monitoring retention, application state и data residency различаются; `store:false` не считается ZDR. MAM/ZDR/residency применяются только через Group C privacy gate.

Group A total: `2`; решения не переоткрыты. ADR сейчас не требуется при сохранении provider-neutral границы и обычного user-scoped RLS-пути.

## 6. Целевая state machine и API

Неизменяемая последовательность: text → new intent → AI interpretation → runtime validation → semantic validation → clarification/continuation либо support/mixed handling → normalized formulation → `ready_to_present` → client render → technical presentation acknowledgement → `presented` → `creating` → atomic transaction → `committed_pending_verification` → post-commit read-only verification → `success | failure | unknown`.

Будущие Route Handlers:

- `POST /api/task-intents`: только новое явное intent, новый UUID.
- `POST /api/task-intents/[operationId]/continuations`: единственный strict continuation (`clarification_answer` либо `supported_only`) с revision/idempotency key.
- `POST /api/task-intents/[operationId]/presentations`: technical acknowledgement только после render, immutable presentation ID/fingerprint.
- `GET /api/task-intents/[operationId]`: read-only status/post-commit reconciliation; после unknown insert не вызывает.

## 8. Supabase contract и порядок migrations

1. Инициализировать local stack/config только после утверждения плана.
2. Migration 1: enum/check types и `task_operations` с owner/session-derived identity, intent/interaction/revision/state, immutable normalized representation, result/proof fields и timestamps.
3. Migration 2: `personal_tasks` с `owner_id`, `text`, unique `source_operation_id`; без необязательных продуктовых свойств.
4. Migration 3: constraints/unique `(owner_id,intent_id)`, continuation delivery, presentation ID и state transition guards.
5. Migration 4: RLS enable/force, authenticated policies только `auth.uid()=owner_id`; owner_id берётся из verified session, не request body.
6. Migration 5: атомарная `SECURITY INVOKER` function: row lock operation, валидный `presented`, переход `creating`, insert-or-observe exactly one task, `committed_pending_verification`; она не пишет `success`.
7. Migration 6: безопасная retention function/metadata без широких прав; запуск отдельно по утверждённому deployment gate.
8. На каждом шаге: local reset, pgTAP schema/RLS/function tests, application integration, dry-run before remote push.

`SECURITY DEFINER`, `BYPASSRLS`, `service_role` и широкий secret запрещены в обычном пользовательском пути. Post-commit verification — отдельное согласованное read-only чтение операции и ровно одной связанной task, затем compare-and-set результата. RLS tests проверяют own/foreign rows, forged owner_id, RPC privileges, rollback и параллельную идемпотентность.

## 9. Vercel contract

Vercel Preview подключается только к Preview Supabase; Production — только к Production. Server-only env vars не имеют `NEXT_PUBLIC_`; значения не логируются и не попадают в client bundle. Functions используют Node.js runtime в `fra1`, `maxDuration=30s`, не полагаются на persistent filesystem. Gates: local production build → Preview deployment → env/project fingerprint → synthetic happy/negative smoke → migrations equality → отдельное разрешение Production → Production deployment и smoke. Финальная сдача невозможна без реально подключённых Supabase/Vercel и проверенного Production deployment.

## 11. Тестовый контракт

- Unit: parsers, semantic rules, state transitions, safe reason mapping, retention calculations.
- Contract: strict HTTP/AI unions, byte/code-point/context limits, continuation kind, immutable IDs/revisions, no unknown fields.
- Integration: Route Handlers with verified session, capability registry, AI stub, Supabase transaction and read-only proof.
- Database/RLS: schema, constraints, own/foreign access, forged owner, SECURITY INVOKER privileges, no broad-secret path.
- Concurrency/idempotency: same intent, repeated continuation, duplicate/parallel presentation acknowledgement, duplicate creating and row locking.
- Browser E2E: supported happy path, ambiguity, mixed request, presentation ordering and all three results.
- Negative/security: stale revision, foreign operation, invalid continuation, mismatched presentation, changed normalized text, rollback/lost response/read error, secret/stack redaction, absence of task text in logs.

Обязательная parameterized матрица включает: один new intent; technical retry; stale revision; foreign operation; critical clarification; mixed request; invalid continuation kind; repeated delivery; ready-to-present retry; no creation before acknowledgement; duplicate/parallel acknowledgement; mismatched ID; changed formulation; exactly one task; duplicate creating retry; rollback; committed-pending-verification; success only after verification; failure only on confirmed absence; unknown on insufficient evidence; no recreation after unknown; RLS isolation; broad secret prohibition; no task text logs.

## 15. Security и privacy gates
