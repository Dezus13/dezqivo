- Тип: техническая спецификация

## 1. Назначение

SPEC-0003 определяет предлагаемый технический контракт реализации утверждённой SPEC-0002 без изменения её продуктового смысла: от текстового намерения создать одну личную задачу до проверяемого результата `success`, `failure` или `unknown` и защиты от автоматического дубликата.

Документ отвечает на технические вопросы SPEC-0002, определяет границы модульного монолита, данные, транзакции, безопасность, развёртывание и проверки. Он не является PLAN и не разрешает создание кода, конфигураций или миграций.

## 3. Область

Технический контракт покрывает только путь:

```text
текстовое намерение
→ интерпретация одной задачи
→ критическое уточнение при необходимости
→ проверка поддержки
→ показ нормализованной формулировки
→ создание ровно одной локальной задачи DEZQIVO
→ success | failure | unknown
→ защита от автоматического дубликата
```

В область входят внутренний HTTP-контракт, контекст текущего взаимодействия, доверенная проверка AI-вывода, локальная операция создания, минимальные данные, транзакция, идемпотентность, пользовательские состояния, безопасные ошибки, наблюдаемость и тестирование.

## 4. Вне области

Не реализуются и не проектируются как поддерживаемые функции:

- голосовой ввод;
- список, поиск и фильтрация задач;
- редактирование, завершение и удаление задач;
- настройки и долгосрочная память;
- Gmail, Google Calendar, авиапоиск и другие внешние сервисы;
- внешние действия и функции этапов 3–8;
- окончательный визуальный дизайн;
- отдельный пользовательский экран авторизации;
- фоновые автоматические повторы создания;
- микросервисы, очередь сообщений и распределённая оркестрация.

Техническая идентификация владельца данных выполняется через Supabase Auth и проверенную пользовательскую серверную сессию без добавления отдельного продуктового экрана авторизации.

## 5. Технические цели и инварианты

1. Один входной запрос создаёт не более одной локальной задачи для одного технического намерения.
2. AI-вывод всегда считается недоверенным и проверяется доверенным кодом.
3. Только серверный слой создаёт операции и задачи.
4. Клиент не получает серверные секреты и не определяет итог операции.
5. `success` устанавливается только после чтения подтверждённой записи задачи, связанной с операцией.
6. `failure` устанавливается только при подтверждённом отсутствии результата.
7. Недостаточность доказательств приводит к `unknown`, а не к предположению.
8. После `unknown` технический retry не создаёт новую задачу.
9. Новое явное намерение имеет новый идентификатор и не блокируется совпадением текста.
10. Нормализованная формулировка, её неизменяемый отпечаток и подтверждённое представление неизменно связываются с операцией, задачей и результатом.
11. Локальная задача принадлежит идентифицированному пользователю DEZQIVO.
12. Создание задачи и фиксация `committed_pending_verification` выполняются в одной транзакционной границе; финальный `success` устанавливается только отдельным контролируемым обновлением после post-commit проверки.

## 7. Границы исполнения

### 7.1. Клиент

Клиент принимает текст, создаёт новый `intent_id` только для нового явного сообщения, повторно использует его при транспортном retry, показывает нормализованную формулировку, уточнение и результат. Клиент не пишет напрямую в таблицы и не определяет `success`.

### 7.2. Доверенный серверный слой

Route Handler принимает запрос, проверяет пользовательскую серверную сессию, структуру, размер по утверждённому техническому лимиту, контекст и `intent_id`; вызывает модули интерпретации, поддержки, оркестрации и хранения. Широкий server secret в обычном пути создания задачи запрещён.

### 7.3. AI-граница

AI получает минимально необходимый текст и допустимый текущий контекст. Он возвращает кандидата интерпретации, но не получает доступ к Supabase, не создаёт задачу, не назначает результат и не формирует неподтверждённую техническую причину.

### 7.4. Хранилище

Supabase Postgres хранит операции создания и личные задачи, применяет ограничения уникальности, внешние ключи, допустимые состояния и RLS. Postgres, а не AI или клиент, является источником истины для факта создания.

## 8. Технический поток запроса

1. Клиент получает новое явное текстовое сообщение и создаёт UUID `intent_id`.
2. Клиент отправляет `POST /api/task-intents` с `intent_id`, текстом, идентификатором текущего взаимодействия и допустимым контекстом.
3. Сервер проверяет пользовательскую сессию Supabase Auth и устанавливает владельца согласно D-005.
4. Сервер валидирует envelope и ищет операцию по `(owner_id, intent_id)`.
5. Для новой операции сервер создаёт один `operation_id`, фиксирует `received`, вызывает AI-адаптер и валидирует его результат.
6. Повторная доставка первичного запроса с тем же `intent_id` не считается новым принятым намерением: сервер возвращает существующую операцию по состоянию. Ожидание пользователя и `ready_to_present` возвращают неизменный снимок без создания; `presented` безопасно продолжает автоматический серверный переход; `creating`, `committed_pending_verification` и `unknown` допускают только сверку без нового insert; терминальный результат возвращается как существующий снимок.
7. При критической неоднозначности фиксируется `clarification_required`; задача не создаётся.
8. При смешанном запросе фиксируется `scope_decision_required`; задача не создаётся до решения пользователя.
9. Ответ на уточнение или решение области принимается только отдельным контрактом продолжения из раздела 9, относится к тому же `operation_id` и `intent_id` и проходит optimistic version check.
10. После новой или допустимо продолженной интерпретации сервер получает актуальную нормализованную формулировку, проверяет поддержку, создаёт неизменяемые `presentation_id` и отпечаток формулировки и сохраняет `ready_to_present`.
11. Сервер возвращает клиенту `ready_to_present`, нормализованную формулировку, `presentation_id` и ревизию; задача не создаётся.
12. После фактического отображения клиент без действия пользователя автоматически отправляет отдельное техническое подтверждение представления. Доверенный сервер проверяет его и фиксирует `presented`.
13. Тот же обработчик автоматически выполняет `presented → creating` без пользовательского подтверждения и вызывает атомарную Postgres-функцию один раз для операции.
14. Транзакция создаёт ровно одну задачу либо безопасно возвращает уже связанную задачу и фиксирует `committed_pending_verification`, но не `success`.
15. После commit сервер выполняет отдельную read-only сверку операции и задачи под той же user-scoped сессией и RLS.
16. Только полное доказательство разрешает отдельное контролируемое обновление до `success`; подтверждённый rollback/отсутствие результата разрешает `failure`; недостаток доказательств приводит к `unknown`.

`operation_id` идентифицирует одну логическую операцию от первого сообщения до терминального результата. `intent_id` неизменен для retries и продолжений этой операции. Ответ на уточнение и решение области не создают новые идентификаторы. Новое явное намерение создаёт новые `operation_id` и `intent_id`.

Полный обязательный путь: новое намерение → интерпретация → при необходимости continuation → актуальная формулировка → `ready_to_present` → фактическое отображение → техническое подтверждение представления → `presented` → `creating` → атомарный commit без `success` → `committed_pending_verification` → read-only post-commit проверка → `success`, `failure` или `unknown`.

`ready_to_present` означает только подготовленную и отправляемую формулировку. Из него создание запрещено. Retry возвращает ту же формулировку, тот же `presentation_id` и актуальную ревизию без перехода к созданию. Ни сохранение формулировки, ни отправка ответа сервером не доказывают отображение.

## 9. Контракт входа и контекста

```ts
type TaskIntentRequest = {
  intent_id: string;               // UUID, новый только для нового явного намерения
  interaction_id: string;          // UUID текущего взаимодействия
  message: string;                 // исходный непустой текст
  context_revision: number;        // монотонная версия допустимого контекста
  additional_after_unknown_of?: string; // operation ID только при явной просьбе
};

type TaskOperationContinuationRequest = {
  operation_id: string;            // UUID существующей логической операции
  expected_revision: number;       // ожидаемая operation.version
  continuation_id: string;         // UUID, стабильный при повторной доставке ответа
  answer:
    | { kind: "clarification_answer"; text: string }
    | { kind: "scope_decision"; value: "supported_only" };
};

type TaskPresentationAcknowledgementRequest = {
  operation_id: string;
  expected_revision: number;       // ревизия показанного ready_to_present
  presentation_id: string;         // неизменяемый ID показанной формулировки
  acknowledgement_id: string;      // UUID, стабильный при retry события показа
};
```

Первичный endpoint предназначен только для нового явного намерения. Его строгая runtime-схема разрешает только поля `TaskIntentRequest` и отклоняет `scope_decision`, `clarification_answer`, `operation_id` существующей операции и любые другие continuation-поля безопасной ошибкой контракта без создания и изменения данных. Новое принятое намерение создаёт новые `operation_id` и `intent_id`; повторная доставка того же первичного сообщения с тем же `intent_id` идемпотентно возвращает созданную им операцию и не продолжает ожидающую ответа операцию.

Ответы пользователя принимаются исключительно отдельным доверенным continuation endpoint через `TaskOperationContinuationRequest` и проверенную пользовательскую сессию. Строгий discriminated union допускает ровно один вариант — `clarification_answer` или `scope_decision`; одновременная передача обоих вариантов и неизвестные поля отклоняются. `owner_id` никогда не принимается как доверенное поле тела.

Для продолжения сервер обязан:

1. загрузить `operation_id` только в области текущего пользователя под RLS;
2. сопоставить владельца с `auth.uid()` и отклонить чужую или невидимую операцию;
3. проверить `expected_revision`, ожидаемое состояние и тип ответа;
4. принять `clarification_answer` только из `clarification_required`, а `scope_decision` — только из `scope_decision_required`;
5. атомарно зарегистрировать уникальный `(owner_id, operation_id, continuation_id)` и привязать ответ к той же операции;
6. продолжить интерпретацию только с подтверждённым контекстом этой операции, не создавая новые `operation_id` и `intent_id`;
7. при повторе того же `continuation_id` вернуть уже достигнутое состояние без повторной интерпретации и создания;
8. при устаревшей ревизии вернуть актуальный безопасный снимок и конфликт ревизии без изменения состояния;
9. отклонить продолжение из любого другого состояния без создания задачи.

После допустимого ответа сервер получает актуальную нормализованную формулировку, повторно проверяет поддержку и создаёт новое представление. Повторная доставка continuation не создаёт новую операцию, представление или задачу.

`TaskPresentationAcknowledgementRequest` — автоматическое техническое событие клиента после фактического отображения, а не пользовательское согласие, кнопка «Да» или подтверждение локального действия. Endpoint принимает только проверенную сессию и четыре указанных технических поля; `owner_id`, `intent_id`, изменяемая формулировка, пользовательский ответ и `confirmed` запрещены.

Сервер обязан загрузить операцию текущего пользователя под RLS, проверить `ready_to_present`, ревизию, `presentation_id` и неизменяемый отпечаток нормализованной формулировки. Он атомарно регистрирует уникальный `(owner_id, operation_id, acknowledgement_id)`, запрещает отличающийся `presentation_id` для той же ревизии и выполняет compare-and-set в `presented`. Повтор того же acknowledgement идемпотентно возвращает достигнутое состояние. Устаревшая ревизия, чужая операция, несовпадающий ID или отпечаток и недопустимое состояние отклоняются без создания.

Только из `presented` доверенный сервер автоматически продолжает `presented → creating`. Два параллельных acknowledgement конкурируют по compare-and-set и уникальности, поэтому только один может запустить создающий переход. Если формулировка изменена до создания, сервер выпускает новые `presentation_id`, отпечаток и ревизию и возвращается в `ready_to_present`; прежнее acknowledgement становится недействительным.

Retry из `ready_to_present` только повторно выдаёт то же представление. Retry после `presented` может продолжить ту же операцию с прежними `operation_id` и `intent_id`; row lock и уникальности исключают второй insert. Без принятого технического подтверждения представления задача не создаётся.

Точный максимальный размер сообщения, срока хранения контекста и способ выпуска `interaction_id` должны быть определены до утверждения PLAN. Сервер выводит владельца только из проверенной Auth-сессии.

Контекст содержит только сообщения текущего взаимодействия, необходимые для интерпретации. Он не является долгосрочной памятью. Сервер связывает `context_revision` с зафиксированной операцией и отклоняет скрытую замену контекста в том же `intent_id`.

## 10. Контракт AI-интерпретации

```ts
type Interpretation =
  | { kind: "create_task"; normalized_text: string }
  | { kind: "clarification"; question: string; ambiguity_code: string }
  | {
      kind: "mixed";
      normalized_text: string;
      unsupported_summary: string;
      scope_question: string;
    }
  | { kind: "unsupported"; capability_code: string };
```

Доверенная runtime-схема требует ровно один вариант, отклоняет неизвестные поля, пустой `normalized_text`, несколько задач, управляющие инструкции и неподдерживаемые capability codes. Свободный текст AI не используется как SQL, причина ошибки, доказательство результата или команда.

Нормализация может менять пробелы и форму изложения, но не добавляет дату, срок, приоритет, напоминание, категорию или описание. Проверяемые правила достаточности и недомысливания реализуются до сохранения операции.

## 11. Проверка поддержки

Внутренний реестр содержит версионированную запись только для `CAP-401.create` этой SPEC. Поддержка истинна, когда одновременно:

- capability присутствует в утверждённом реестре реализации;
- обработчик включён и прошёл health/configuration check;
- интерпретация относится ровно к одной локальной задаче;
- запрос не требует функции вне области.

Статус `selected` или наличие CAP в документации не является доказательством фактической поддержки. Смешанная и неподдерживаемая части возвращаются структурированно; они не направляются в универсальный исполнитель.

## 12. Модель локальной задачи

Минимальная задача содержит:

```text
id                 UUID, primary key
owner_id           UUID, not null
title              text, not null, непустое после нормализации
source_operation_id UUID, not null, unique
created_at         timestamptz, not null, server-generated
```

Дата, время, срок, приоритет, напоминание, категория, описание и статус завершения не добавляются. `source_operation_id` обеспечивает доказуемую связь с нормализованной формулировкой и результатом.

## 13. Модель операции создания

```text
id                         UUID, primary key
owner_id                   UUID, not null
intent_id                  UUID, not null
interaction_id             UUID, not null
context_revision           bigint, not null
request_text               text, not null
normalized_text            text, nullable до интерпретации
normalized_fingerprint     text, nullable до подготовки представления
presentation_id            UUID, nullable до подготовки представления
state                      operation_state, not null
result_kind                success | failure | unknown | null
safe_reason_code           text, nullable
created_task_id            UUID, nullable
additional_after_unknown_of UUID, nullable
created_at                 timestamptz, not null
updated_at                 timestamptz, not null
version                    bigint, not null
```

Технический журнал продолжений содержит `owner_id`, `operation_id`, уникальный `continuation_id`, ожидавшуюся ревизию, тип ответа и достигнутую ревизию. Он не является новой продуктовой сущностью и нужен только для идемпотентной обработки ответа пользователя.

Технический журнал подтверждений представления содержит `owner_id`, `operation_id`, уникальный `acknowledgement_id`, `presentation_id`, ожидавшуюся ревизию и достигнутую ревизию. Он доказывает получение сервером автоматического события клиента после отображения, но не является пользовательским согласием.

Ограничения:

- `unique(owner_id, intent_id)`;
- `unique(created_task_id)` при ненулевом значении;
- `created_task_id` ссылается на задачу того же владельца;
- `success` требует ненулевые `created_task_id` и `normalized_text`;
- `failure` требует отсутствия `created_task_id`;
- `unknown` не делает утверждение о наличии задачи;
- `additional_after_unknown_of` допустим только для новой операции и ссылается на `unknown` того же владельца.
- `(owner_id, operation_id, continuation_id)` уникален для технической повторной доставки продолжения;
- `(owner_id, operation_id, acknowledgement_id)` уникален для повторной доставки события отображения;
- `owner_id` операции и задачи всегда равен идентификатору проверенной Auth-сессии и не берётся из запроса;
- `ready_to_present` требует `normalized_text`, `normalized_fingerprint` и `presentation_id`, но запрещает связанную задачу;
- `presented` требует применённое подтверждение текущих `presentation_id`, ревизии и отпечатка;
- `committed_pending_verification` требует связанную задачу, но запрещает `result_kind=success`.

Хранение исходного текста и срок retention требуют решения владельца; минимизация может заменить `request_text` защищённым диагностическим отпечатком после завершения.

## 14. Состояния и переходы операции

| Состояние | Допустимые следующие состояния |
|---|---|
| `received` | `clarification_required`, `scope_decision_required`, `unsupported`, `ready_to_present`, `failure` |
| `clarification_required` | `received`, `failure` |
| `scope_decision_required` | `received`, `failure` |
| `unsupported` | терминальное |
| `ready_to_present` | `presented` — только после валидного технического подтверждения отображения; создание запрещено |
| `presented` | `creating` — автоматический доверенный серверный переход |
| `creating` | `committed_pending_verification`, `failure`, `unknown` |
| `committed_pending_verification` | `success`, `unknown` |
| `success` | терминальное |
| `failure` | терминальное |
| `unknown` | `success` только после безопасной read-only сверки полного доказательства; создание повторно не вызывается |

Переходы выполняются сервером с optimistic version check. `clarification_required → received` допускает только ответ `clarification_answer`; `scope_decision_required → received` — только `scope_decision=supported_only`. Устаревшая ревизия, неверный тип ответа, чужая операция и любое продолжение из недопустимого состояния не меняют операцию и не создают задачу. Повторный `continuation_id` возвращает уже достигнутую ревизию. `ready_to_present` не имеет перехода в `creating`; только валидное acknowledgement создаёт `presented`. Повторный запрос терминальной операции возвращает существующий снимок. Новое намерение после `success`/`failure` имеет новый `intent_id`; после `unknown` дополнительная операция требует `additional_after_unknown_of` и проверенного явного пользовательского текста.

## 15. Установление результата и доказательства

| Результат | Необходимое доказательство | Запрещено |
|---|---|---|
| `success` | Отдельная post-commit read-only сверка подтвердила принятое acknowledgement текущего представления, ровно одну задачу текущего владельца, правильные `operation_id` и `intent_id`, совпадение с показанной normalized text/отпечатком и согласованное состояние; после этого выполнено отдельное контролируемое обновление результата | Успех внутри создающей транзакции, без доказанного представления, по AI-ответу, HTTP 2xx или факту начала |
| `failure` | Транзакция подтверждённо отклонена/откачена либо проверенный precondition исключил создание; связанная задача отсутствует | Подменять неизвестность failure |
| `unknown` | Ответ транзакции потерян, commit неопределён, post-commit чтение завершилось ошибкой или доказательств для success/failure недостаточно | Ошибку чтения считать failure, автоматически повторять создание или делать предположение |

`safe_reason_code` берётся только из доверенного перечня (`invalid_input`, `unsupported`, `storage_rejected`, `identity_unavailable`, `result_unverifiable`). Пользовательский текст причины формируется из кода и подтверждённых фактов, а не из сырой ошибки или AI.

## 16. Идемпотентность и поведение после unknown

1. Клиент создаёт `intent_id` при новом явном сообщении.
2. Транспортный retry сохраняет `intent_id`.
3. Уникальность `(owner_id, intent_id)` создаёт или возвращает одну операцию.
4. `source_operation_id` допускает максимум одну задачу на операцию.
5. Postgres-функция блокирует строку операции и идемпотентно создаёт или возвращает связанную задачу без установки `success`.
6. После потери ответа сервер выполняет только read-only сверку операции и задачи; повторно не вызывает insert.
7. Если состояние установить невозможно, возвращается `unknown`.
8. Новое идентичное намерение после `success`/`failure` получает новый `intent_id` и разрешено.
9. После `unknown` технический retry или явный запрос статуса выполняет только read-only сверку: она не меняет `intent_id`, не создаёт задачу и может установить `success` отдельным обновлением только при полном доказательстве; иначе сохраняется `unknown`.
10. После `unknown` новый `intent_id` разрешён только с явной просьбой о дополнительной задаче и ссылкой на исходную unknown-операцию.

Хэш текста не используется как ключ: он ошибочно блокировал бы новое идентичное намерение.

## 17. Supabase, целостность и транзакции

Supabase используется для Postgres, миграций и Auth. Storage, Realtime и Edge Functions не требуются текущей областью.

Серверная Postgres-функция `create_personal_task_once(operation_id, expected_version)`:

1. выполняется в транзакции;
2. выполняется как `SECURITY INVOKER` от проверенной user-scoped сессии под RLS;
3. блокирует существующую операцию текущего пользователя `FOR UPDATE`;
4. проверяет `auth.uid()`, состояние `presented`, ожидаемую версию, `intent_id`, применённый `presentation_id` и неизменяемую normalized text/отпечаток;
5. обеспечивает уникальность `(owner_id, intent_id)` и при существующей связанной задаче возвращает её без insert;
6. создаёт ровно одну задачу с `owner_id`, `source_operation_id` и связью с `intent_id` и показанной формулировкой;
7. обновляет операцию до `committed_pending_verification`, связывает task ID и не записывает `success`;
8. возвращает operation/task identifiers;
9. при исключении откатывает создание задачи и изменение операции.

После commit доверенный сервер отдельным read-only запросом под той же user-scoped сессией и RLS подтверждает: принятое acknowledgement текущих `presentation_id`, ревизии и отпечатка; ровно одну задачу; текущего владельца; правильные `operation_id` и `intent_id`; соответствие показанной normalized text/отпечатку; согласованность операции и задачи; отсутствие второй задачи для операции. Только затем отдельный compare-and-set по ожидаемой версии переводит `committed_pending_verification` или доказанный `unknown` в `success`. Этот update не создаёт задачу и повторно проверяет связь результата.

Подтверждённый rollback либо подтверждённое отсутствие результата разрешает отдельный переход в `failure`. Потерянный ответ, неопределённый commit и ошибка post-commit чтения дают `unknown`; ошибка чтения не является доказательством failure. После `unknown` создание никогда не вызывается автоматически, разрешена только безопасная read-only сверка.

Прямой клиентский write запрещён. Все функции обычного пользовательского пути выполняются как `SECURITY INVOKER`; `SECURITY DEFINER`, роль с `BYPASSRLS`, `service_role` и любой широкий server secret в этом пути запрещены. RLS применяется ко всем пользовательским таблицам и ограничивает select/insert/update по `owner_id = auth.uid()`. Пользователь не передаёт доверенный `owner_id`: владелец определяется только из проверенной Auth-сессии. Миграционные и административные права отделены и недоступны пользовательскому endpoint; их возможное будущее применение требует отдельного разрешения, проверки угроз и повторной оценки ADR.

## 18. Миграции и откат

- Схема создаётся только будущим утверждённым PLAN.
- Каждая миграция имеет монотонное имя, review и проверку на чистой БД.
- Миграции сначала добавляют типы, таблицы, constraints, индексы, функцию и RLS; затем включают приложение.
- Откат до появления пользовательских данных может удалить созданные объекты обратной миграцией.
- После появления данных предпочтительна исправляющая forward-миграция; destructive rollback требует резервной копии и отдельного разрешения.
- Миграция не считается успешной, пока ограничения и RLS не проверены интеграционными тестами.

## 19. Vercel и границы развёртывания

Vercel используется как единая целевая платформа модульного монолита:

- Git-интеграция создаёт Preview для рабочих веток и Production из утверждённой основной ветки;
- Next.js Route Handlers исполняются как Vercel Functions в серверном runtime;
- AI и Supabase secrets доступны только Functions;
- клиентский bundle получает только явно публичную конфигурацию;
- локальная файловая система Functions не используется как источник истины;
- Postgres остаётся постоянным хранилищем;
- deployment ID добавляется в диагностические события без пользовательского содержания.

Производственное развёртывание не разрешается этим draft. Совместимые регионы, runtime, лимиты выполнения, план Vercel и разделение инфраструктуры Preview/Production должны быть определены до утверждения PLAN, если это не меняет продуктовые требования SPEC-0002.

## 21. Пользовательские состояния и безопасные ошибки

Техническое представление обязано различать:

- ввод/обработка;
- `clarification_required` с одним вопросом;
- `scope_decision_required` с обеими частями;
- `ready_to_present` с нормализованной формулировкой;
- `presented` как внутреннее доказанное состояние без нового пользовательского решения;
- `success`, `failure`, `unknown`;
- неподдерживаемую возможность и безопасный следующий шаг.

Состояния имеют текстовое обозначение и не различаются только цветом. Фокус и статусные сообщения доступны assistive technologies. Тексты ошибок строятся из безопасных кодов. Stack trace, SQL, prompt, ключи, идентификаторы инфраструктуры и сырой ответ AI пользователю не показываются.

## 22. Журналирование и диагностика

Структурированное событие содержит: timestamp, environment, deployment ID, operation ID, interaction ID, state transition, capability code, safe reason code, duration bucket и correlation ID. По умолчанию не журналируются request text, normalized text, context, session token, SQL, prompt и AI response.

Уровни доступа и retention должны быть определены до утверждения PLAN. Диагностика должна позволять установить переход и техническую попытку, но не используется как единственное доказательство создания задачи: доказательство находится в Postgres.

## 24. Стратегия тестов

- Unit: достаточность, нормализация, state machine, safe error mapping, intent/retry classification.
- Contract: первичный request без continuation-полей и с их обязательным отклонением; единственный strict continuation union без одновременных вариантов; presentation acknowledgement; допустимые состояния/ревизии; повторные delivery ID; AI discriminated union, включая неизвестные поля и malformed output.
- Integration с изолированным Supabase/Postgres: constraints, user-scoped RLS, `SECURITY INVOKER`, запрет обхода RLS, transaction rollback, отсутствие `success` внутри создающей транзакции, concurrent idempotency и post-commit result proof.
- Server integration: Route Handler, identity, capability registry, AI adapter stub; единственный continuation-путь после уточнения и mixed decision; `ready_to_present` без insert; acknowledgement → `presented`; автоматический `presented → creating`; чужая операция, устаревшая ревизия, несовпадающее представление, недопустимое состояние и повторная доставка.
- Concurrency: два acknowledgement одного представления, retry после `presented` и параллельные запросы одного `intent_id` создают ровно одну задачу.
- Fault integration: ошибка post-commit чтения, потерянный ответ транзакции, подтверждённый rollback, read-only сверка после `unknown` и отсутствие повторного создания.
- Browser E2E: показ актуальной формулировки, уточнение, смешанный запрос, три результата, отсутствие отдельного подтверждения и создание ровно одной задачи.
- Manual accessibility/security: клавиатура, screen reader announcement, отсутствие секретов в client bundle/logs/errors.

Тесты должны быть детерминированы; AI заменяется contract stub в автоматической приёмке. Проверка реального поставщика является отдельной ограниченной интеграционной проверкой.

## 27. Ответы на 11 вопросов SPEC-0002

1. **Вход и контекст:** первичный `TaskIntentRequest` только для нового сообщения; отдельные strict continuation и presentation contracts; `interaction_id`, `context_revision`, серверная идентичность и только текущий контекст.
2. **Достаточность, неоднозначность, нормализация:** AI discriminated union, runtime/trusted валидация, единственный state-aware continuation и неизменяемое представление с acknowledgement после render.
3. **Ровно одна задача:** запрет create из `ready_to_present`, автоматический `presented → creating`, уникальные intent/continuation/acknowledgement и `source_operation_id`, row lock и атомарная Postgres-функция.
4. **Хранение и минимум данных:** Supabase Postgres; две минимальные сущности из разделов 12–13 без необязательных продуктовых свойств.
5. **Результаты:** `committed_pending_verification`, отдельная post-commit сверка и discriminated `result_kind`; создающая транзакция не пишет `success`.
6. **Доказательства:** post-commit согласованное read-only чтение операции и ровно одной задачи; подтверждённый rollback/отказ; ошибка чтения или недостаток сведений дают unknown.
7. **Защита повтора:** стабильный `intent_id` на retries и новый ID на новое намерение; текст не является ключом.
8. **Классификация повторов:** тот же `intent_id` и state-aware переход — retry/продолжение той же операции; новый ID — новое намерение; после unknown status retry только сверяет, а дополнительная задача требует `additional_after_unknown_of` и явный текст.
9. **Связь результата:** immutable normalized text в операции, unique source operation в задаче и created task ID в результате.
10. **Секреты и ошибки:** серверные env vars, safe reason allowlist, redaction и структурированные логи без payload.
11. **Проверки AC:** матрица раздела 26 задаёт автоматическую и, где нужна, ручную проверку каждого `AC-001`–`AC-026`.

## 29. Решения владельца и отложенные технические вопросы

Владелец принял рекомендуемый пакет D-001–D-013 для доработки draft SPEC-0003:

1. Приняты TypeScript со строгой типизацией, Next.js App Router как единый модульный монолит, Vercel и Supabase Postgres.
2. Приняты Supabase Auth, проверенная пользовательская серверная сессия и RLS; широкий server secret запрещён в обычном пути создания задачи.
3. Принят нейтральный к поставщику AI-адаптер, строгий JSON-контракт и обязательная runtime-валидация доверенным кодом.
4. Приняты UUID `intent_id`, уникальность `(owner_id, intent_id)` и атомарная Postgres-транзакция операции, задачи и результата.
5. Приняты стратегия unit/contract/integration/browser E2E, минимальные структурированные логи без текста задач и секретов, lockfile и поддерживаемая LTS-линия Node.js.
6. ADR сейчас не требуется; необходимость ADR повторно проверяется при выборе AI-поставщика либо при предложении обхода RLS.

До утверждения активного PLAN требуется отдельное проверяемое техническое решение о конкретных AI-поставщике и модели.

До утверждения PLAN разрешено определить точные совместимые версии, package manager, библиотеку runtime-валидации, тестовые инструменты, технические лимиты, retention и совместимые регионы при условии, что они не меняют продуктовые требования SPEC-0002.

Это решение не утверждает SPEC-0003 и не разрешает реализацию.

## 30. Риски и меры контроля

| Риск | Мера контроля |
|---|---|
| AI добавляет свойства или несколько задач | Строгая union schema, trusted validator, negative contract tests |
| Дубликат из concurrent retry | Две уникальности, row lock, одна DB-транзакция, concurrency tests |
| Ложный success после потери ответа | Создающая транзакция пишет только `committed_pending_verification`; отдельные post-commit verification и success update; unknown без автоматического insert |
| Создание до фактического показа формулировки | `ready_to_present` запрещает insert; только валидное acknowledgement создаёт `presented`, из которого разрешён creating |
| Вечная дедупликация одинакового текста | UUID намерения вместо text hash |
| Дополнительная задача после unknown без согласия | Новая операция требует ссылки и явного текста |
| Обход владельца данных | Server identity, RLS, owner constraints, cross-user tests |
| Утечка текста/секретов | Server-only env, no payload logs, redaction tests |
| Preview пишет в Production | Раздельные env vars и предпочтительно отдельные Supabase projects |
| Зависимость от AI/платформы | Адаптеры, version-neutral contracts, lockfile и ADR |
| Scope creep | Capability allowlist и отсутствие модулей последующих этапов |
