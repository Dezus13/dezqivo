# SPEC-0001: Документационный фундамент

## Метаданные

- Идентификатор: `SPEC-0001`
- Тип: техническая спецификация
- Статус: `approved`
- Версия: `0.2.2`
- Дата создания: `2026-07-13`
- Утверждение: владелец проекта, 2026-07-20
- Связанный план: `PLAN-0001`

**Источник истины** — единственный документ, который определяет конкретный тип информации. Остальные документы могут ссылаться на него, но не должны дублировать, изменять или переопределять его содержание. В дальнейшем термин используется только в этом смысле.

## 1. Цель этапа

Создать минимальный, однозначный и масштабируемый документационный фундамент DEZQIVO для разработки по Specification Driven Development (SDD).

Фундамент должен разделять бизнес-контекст, системные требования, функции, пользовательские сценарии, техническую архитектуру, спецификации, планы и историю изменений. Каждый вид информации должен иметь один источник истины без дублирования между документами.

Результат этапа должен позволить новому разработчику или AI-инструменту понять назначение проекта, найти действующие требования, определить разрешённую область работы и проследить изменение от исходной потребности до документированного результата.

## 2. Область изменений

Этап охватывает только:

- создание корневых документов управления проектом;
- создание фундаментальных содержательных документов в `docs/`;
- определение структуры спецификаций и планов;
- создание файла `изменения.md`;
- закрепление единого нормативного источника правил работы AI-инструментов;
- настройку технологически нейтрального `.gitignore`;
- установление правил именования и трассируемости;
- определение проверяемых требований к структуре, ссылкам, языку, безопасности и отсутствию мусора.

## 3. Границы этапа

### 3.1. Входит в этап

- только документационный фундамент, перечисленный в этой спецификации;
- один технический документ `SPEC-0001`;
- один именованный план `PLAN-0001` для реализации документационного фундамента;
- единый нормативный источник процесса разработки в будущем `AGENTS.md`.

### 3.2. Не входит в этап

- программный код;
- приложение и пользовательский интерфейс;
- `package.json` и другие package-файлы;
- каталоги `src/`, `tests/`, `infra/`;
- CI/CD и конфигурация приложения;
- выбор языка программирования, фреймворка, базы данных или облачной платформы;
- инструкции по работе с Supabase, Vercel и другими неутверждёнными технологиями;
- реализация продуктовых функций;
- создание функциональных спецификаций без реальной функции;
- создание ADR без реального долговременного архитектурного решения;
- создание исполняемых AI-навыков до утверждения первой стабильной повторяемой процедуры;
- лицензирование и публикация проекта.

## 4. Структура проекта

### 4.1. Целевая структура при активном плане

```text
DEZQIVO/
├── .gitignore
├── README.md
├── AGENTS.md
├── CLAUDE.md
├── SKILLS.md
├── изменения.md
├── docs/
│   ├── бизнес-контекст.md
│   ├── глобальная-спецификация.md
│   ├── карта-функций.md
│   ├── пользовательские-истории.md
│   ├── техническая-архитектура.md
│   ├── дорожная-карта.md
│   └── specs/
│       └── технические/
│           └── spec-0001-документационный-фундамент.md
└── plans/
    └── active/
        └── plan-0001-документационный-фундамент.md
```

### 4.2. Целевая структура после завершения плана

Завершённый план сохраняет имя и перемещается без копирования:

```text
plans/
└── completed/
    └── plan-0001-документационный-фундамент.md
```

Остальные элементы структуры сохраняются без изменений относительно раздела 4.1.

После перемещения пустой каталог `plans/active/` не сохраняется.

### 4.3. Условные элементы будущих этапов

Следующие элементы не создаются в рамках данного этапа:

```text
docs/specs/функциональные/spec-NNNN-русское-название.md
docs/архитектурные-решения/adr-NNNN-русское-название.md
.agents/
.claude/
skills/
SKILL.md
src/
tests/
infra/
```

Каждый условный каталог появляется только одновременно с первым утверждённым содержательным файлом соответствующего типа.

## 5. Назначение документов

| Документ | Источник истины для |
|---|---|
| `README.md` | Короткая точка входа: название, миссия, статус, назначение репозитория, порядок чтения и ссылка на активный план либо явное сообщение об его отсутствии. |
| `AGENTS.md` | Единственный нормативный источник обязательных правил работы AI-инструментов и процесса разработки. |
| `CLAUDE.md` | Технический адаптер Claude Code, содержащий только `@AGENTS.md`. |
| `SKILLS.md` | Неисполняемый реестр повторяемых процедур, их границ, зрелости и будущих связей с исполняемыми AI-навыками. |
| `изменения.md` | Значимые завершённые изменения и их связи со спецификациями, планами и документированными результатами изменений. |
| `docs/бизнес-контекст.md` | Причины существования DEZQIVO: проблема, ценность, заинтересованные стороны, цели, нецели и бизнес-ограничения. |
| `docs/глобальная-спецификация.md` | Границы и поведение DEZQIVO как целостной системы, глобальные требования и инварианты. |
| `docs/карта-функций.md` | Единый каталог возможностей, их границ, состояния, зависимостей и связей со спецификациями. |
| `docs/пользовательские-истории.md` | Пользовательские цели и основные сквозные сценарии без технической реализации. |
| `docs/техническая-архитектура.md` | Актуальное утверждённое устройство системы в целом, её технические границы и ограничения. |
| `docs/дорожная-карта.md` | Последовательность этапов развития, приоритеты, зависимости и ожидаемые результаты. |
| Функциональная спецификация | Наблюдаемое поведение одной ограниченной функции, включая `FR`, `NFR` и `AC`, без способа реализации. |
| Техническая спецификация | Технический контракт реализации утверждённого объёма без добавления продуктовых требований. |
| Активный план | Единственный разрешённый объём текущей работы, порядок действий и проверки. |
| Завершённый план | Фактический результат этапа, выполненные проверки и связи с документированным результатом изменения. |
| ADR | Причина, варианты и последствия отдельного долговременного и труднообратимого архитектурного решения. |

## 6. Правила именования

1. Все обычные имена файлов используют lowercase `kebab-case`.
2. Содержательные части имён Markdown-файлов пишутся на русском языке.
3. Разрешённые исключения для имён файлов: `README.md`, `AGENTS.md`, `CLAUDE.md`, `SKILLS.md`, `SKILL.md`.
4. Системные и конфигурационные файлы, включая `.gitignore`, сохраняют технические имена.
5. Имена спецификаций имеют вид `spec-NNNN-русское-название.md`.
6. Имена планов имеют вид `plan-NNNN-русское-название.md`.
7. Имена архитектурных решений имеют вид `adr-NNNN-русское-название.md`.
8. В реальном имени вместо `NNNN` всегда используется четырёхзначный номер.
9. Внутри документов идентификаторы записываются прописными: `SPEC-0001`, `PLAN-0001`, `ADR-0001`, `FR-001`, `NFR-001`, `AC-001`.
10. Идентификаторы `SPEC`, `PLAN` и `ADR` уникальны во всём репозитории.
11. Идентификаторы `FR`, `NFR` и `AC` нумеруются внутри конкретной спецификации и цитируются составной ссылкой, например `SPEC-0001/AC-003`.
12. Имена каталогов должны быть строчными, однозначными и соответствовать утверждённому дереву.

## 7. Функциональные требования

### FR-001. Минимальный фундамент

Репозиторий должен соответствовать применимому состоянию из раздела 4 и не содержать дополнительных проектных файлов вне утверждённой области.

### FR-002. Короткий README

`README.md` должен содержать только название и миссию DEZQIVO, текущий статус, назначение репозитория, порядок чтения и ссылку на активный план. Если активного плана нет, это должно быть указано явно. Правила запуска добавляются только после появления приложения.

### FR-003. Единые правила AI-инструментов

`AGENTS.md` должен быть единственным нормативным источником обязательных правил работы AI-инструментов, SDD-шлюзов и процесса управления версиями. Другие документы не должны дублировать или переопределять эти правила.

### FR-004. Адаптер Claude Code

`CLAUDE.md` должен содержать ровно строку `@AGENTS.md` и завершающий перевод строки. Отдельные правила Claude Code запрещены без отдельной утверждённой необходимости.

### FR-005. Реестр процедур

`SKILLS.md` должен определять ненормативный реестр повторяемых процедур, границы каждой процедуры, критерии её стабильности, правило переноса в исполняемый AI-навык `SKILL.md` и ссылки на существующие навыки после их появления. Документ не должен дублировать или переопределять `AGENTS.md`.

### FR-006. История изменений

`изменения.md` должен быть создан в рамках этапа и фиксировать только значимые завершённые изменения. Записи должны ссылаться на связанные `SPEC`, `PLAN` и документированный результат изменения, но не копировать историю репозитория.

### FR-007. Разделение уровней документации

Бизнес-контекст, глобальная спецификация, карта функций, пользовательские истории, техническая архитектура и дорожная карта должны быть отдельными содержательными документами с ответственностью из раздела 5.

### FR-008. Разделение спецификаций

Функциональные и технические спецификации должны храниться раздельно без дополнительной вложенности. Каталог соответствующего типа создаётся только вместе с первой реальной спецификацией этого типа.

### FR-009. Жизненный цикл планов

Одновременно допускается не более одного активного плана. Во время реализации этапа должен существовать ровно один файл в `plans/active/`. После завершения тот же файл без переименования перемещается в `plans/completed/`.

### FR-010. Отсутствие пустых каталогов

Пустые каталоги, `.gitkeep` и каталоги «на будущее» запрещены.

### FR-011. Архитектурные решения по необходимости

Каталог `docs/архитектурные-решения/` и файл ADR создаются только для реального долговременного, межкомпонентного или дорого обратимого решения, которое недостаточно зафиксировать в технической архитектуре или технической спецификации.

### FR-012. Трассируемость

Документационный фундамент должен поддерживать следующую цепочку связей:

```text
бизнес-контекст
→ глобальная спецификация
→ элемент карты функций
→ функциональная и при необходимости техническая SPEC
↔ связанная пользовательская история
→ активный PLAN
→ реализация и проверка по AC
→ документированный результат изменения
→ запись в изменения.md
```

Для текущего этапа применима цепочка `SPEC-0001` → `PLAN-0001` → результат проверки по `AC` → документированный результат этапа → `изменения.md`.

### FR-013. Проверяемые ссылки

Связи между репозиторными документами должны использовать относительные Markdown-ссылки и не должны вести к отсутствующим файлам.

### FR-014. Технологически нейтральный `.gitignore`

`.gitignore` должен исключать только системный и редакторский мусор, локальные секреты и `.env`-файлы. Правила конкретного стека запрещены до его утверждения.

### FR-015. Единый источник процесса разработки

Обязательный процесс разработки должен определяться только в `AGENTS.md`. `SKILLS.md` может описывать ненормативные способы выполнения повторяемых процедур, но не может изменять требования `AGENTS.md`.

### FR-016. Запрет программного кода

В рамках этапа запрещено создавать приложение, исходный код, тестовый код, package-файлы, CI/CD и конфигурацию программного стека.

### FR-017. Разрешение противоречий

Более узкий документ может уточнять более общий, но не противоречить ему. План не может изменять требования или архитектурные решения. Противоречия должны устраняться в документе — источнике истины по процессу из `AGENTS.md`.

### FR-018. Условное создание навыков

Каталоги `.agents/`, `.claude/`, `skills/` и исполняемый AI-навык `SKILL.md` запрещено создавать до утверждения первой стабильной повторяемой процедуры.

## 8. Нефункциональные требования

### NFR-001. Минимализм

Каждый файл и каталог должен иметь необходимое назначение в текущем этапе. Структура не должна содержать запасных, пустых или дублирующих артефактов.

### NFR-002. Понятность

Новый разработчик должен понимать назначение и связи документов без устных пояснений.

### NFR-003. Однозначность

Для каждого типа информации должен существовать один источник истины.

### NFR-004. Поддерживаемость

Документы должны быть небольшими по области ответственности, связными и пригодными для независимого обновления без каскадного копирования текста.

### NFR-005. Проверяемость

Каждое требование этапа должно иметь стабильный идентификатор и быть покрыто хотя бы одним критерием приёмки.

### NFR-006. Переносимость

Документация должна храниться в Markdown и UTF-8, использовать относительные ссылки и корректно читаться стандартными инструментами работы с репозиторием.

### NFR-007. Безопасность

Репозиторий не должен содержать секреты, токены, пароли, приватные ключи, реальные `.env`-файлы или персональные данные.

### NFR-008. Аудируемость

По идентификаторам, завершённому плану, `изменения.md` и истории репозитория должна восстанавливаться связь между утверждённым объёмом, выполненными проверками и результатом этапа.

### NFR-009. Языковая согласованность

Вся содержательная документация должна быть написана на русском языке. Код, API, команды, имена библиотек и технические идентификаторы сохраняются на английском языке.

## 9. Критерии приёмки

### AC-001. Соответствие дереву

Фактическое дерево репозитория совпадает с разделом 4 для текущего состояния этапа.

### AC-002. Отсутствие лишних артефактов

Проверка дерева не обнаруживает пустых каталогов, `.gitkeep`, временных файлов, программного кода, package-файлов, `src/`, `tests/`, `infra/` или неутверждённых конфигураций.

### AC-003. Корректные имена

Имена файлов, каталогов и внутренние идентификаторы соответствуют правилам раздела 6.

### AC-004. Русский язык

Вся содержательная документация написана на русском языке, кроме разрешённых технических элементов, и хранится в Markdown и UTF-8.

### AC-005. Единые правила AI

Обязательные правила работы AI-инструментов и процесса разработки находятся только в `AGENTS.md`, а `CLAUDE.md` содержит ровно `@AGENTS.md` и завершающий перевод строки.

### AC-006. Корректное назначение SKILLS

`SKILLS.md` является ненормативным реестром процедур, не дублирует `AGENTS.md`; каталоги навыков и `SKILL.md` отсутствуют.

### AC-007. Разделение источников истины

Каждый обязательный документ содержателен и соответствует своей ответственности из раздела 5; дублирование источников истины отсутствует.

### AC-008. Рабочие ссылки

Все существующие относительные Markdown-ссылки разрешаются в существующие файлы и корректные заголовки.

### AC-009. Жизненный цикл плана

Одновременно существует не более одного активного плана. В завершённом состоянии тот же файл находится только в `plans/completed/`, а пустой каталог `plans/active/` отсутствует.

### AC-010. История изменений

`изменения.md` содержит только значимое завершённое изменение этапа и ссылки на `SPEC-0001`, `PLAN-0001` и документированный результат изменения.

### AC-011. Трассируемость

`PLAN-0001` ссылается на требования и критерии `SPEC-0001`; завершённый план содержит результаты проверок по `AC`; связь с `изменения.md` и документированным результатом этапа не разрывается.

### AC-012. Безопасность

Проверка репозитория не обнаруживает секретов, реальных `.env`-файлов, ключей, токенов или персональных данных; `.gitignore` содержит только технологически нейтральные правила из `FR-014`.

### AC-013. Единый процесс разработки

Подробный обязательный процесс разработки определён только в `AGENTS.md` и не дублируется в других документах. Фактический результат этапа соответствует этому процессу.

### AC-014. SDD-шлюзы

Соблюдение шлюзов утверждения спецификации, плана и реализации подтверждено способом, установленным `AGENTS.md`.

### AC-015. Полнота фундаментальных документов

Каждый обязательный документ содержит сведения в пределах своей ответственности и не является пустым шаблоном или набором необработанных заглушек.

## 10. Риски

| Риск | Последствие | Снижение риска |
|---|---|---|
| Дублирование информации | Источники истины расходятся | Закрепить одного владельца каждого типа информации и использовать ссылки. |
| Преждевременное расширение области | Появляются неутверждённые функции и файлы | Ограничить состав артефактами раздела 4 и `FR-001`. |
| Преждевременный выбор технологий | Архитектура фиксирует неподтверждённые решения | Описывать только утверждённое и явно отмечать неизвестное. |
| Размывание нормативного источника | Правила и процедуры начинают противоречить друг другу | Соблюсти `FR-003` и `FR-005`. |
| Потеря идентичности плана | История этапа становится неаудируемой | Перемещать тот же именованный файл из `active` в `completed`. |
| Битые ссылки | Документация теряет навигацию и трассируемость | Выполнить `AC-008`. |
| Секреты в репозитории | Компрометация доступа и данных | Соблюсти `FR-014` и `AC-012`. |
| Проблемы с кириллическими путями | Инструменты некорректно обрабатывают файлы | Использовать UTF-8 и проверить совместимость Markdown и инструментов репозитория. |

## 11. Ограничения

- Область этапа ограничена документационным фундаментом.
- Новые продуктовые функции запрещены.
- Новые технологии и интеграции не выбираются.
- Пустые каталоги и файлы без содержательного назначения запрещены.
- Все изменения должны быть понятны по содержимому репозитория без дополнительных объяснений.
- Утверждение, планирование, реализация и завершение этапа выполняются по обязательному процессу из `AGENTS.md`.

## 12. Definition of Done

Этап считается завершённым, когда одновременно выполнены все условия:

1. Репозиторий соответствует целевой структуре из раздела 4.
2. Все `FR` и `NFR` проверены соответствующими `AC`.
3. Документы содержательны, написаны на русском языке и имеют непересекающиеся области ответственности.
4. Ссылки и трассируемость между `SPEC-0001`, `PLAN-0001`, результатами проверок, документированным результатом этапа и `изменения.md` не разорваны.
5. Структура не содержит пустых каталогов, мусора, секретов и программного кода.
6. Завершённый `PLAN-0001` содержит результаты проверки всех `AC` и находится только в `plans/completed/`.
7. Все обязательные проверки, определённые `AGENTS.md`, успешно выполнены.
